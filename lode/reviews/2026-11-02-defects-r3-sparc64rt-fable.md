# Round-3 remediation review: `b7c6514` vs `001f2b1` (sparc64rt)

Static review only. No builds, tests, Docker, or QEMU were run, so the commit's "make test green / parity 32 PASS" claim is unverified here. Five tool turns were used: the audit report, the commit stat and line counts, the full source diff, and two targeted cross-reference lookups.

## Per-item verification

**S64-R3-1 (cross-thread DBT invalidation): VERIFIED.**
A shared generation counter now exists in `src/vm/vm64.c:634` and is bumped inside `vm64_txn_commit` at `src/vm/vm64.c:868`. The mmap/munmap/mprotect/mremap shells all commit through `vm64_stxn_commit`, which delegates to `vm64_txn_commit` at `src/vm/vm64.c:832`, so every 6-step mapping change publishes a new generation. The truncate resize path, which runs outside the 6-step legs, bumps explicitly at `src/os/guest_run_sysmem_file.c:506`, and exec image replacement bumps at `src/os/guest_run.c:680`. Readers are in place: the DBT loop snapshots and full-flushes on mismatch before each `sparc64_dbt_run` at `src/os/guest_engines.c:316`, and the futex wait path re-checks on lock reacquisition at `src/os/threads.c:440`. The futex-path flush targets `g->dbt`, which may be a sibling's instance since `g` is shared, but the loop-top check in the resuming thread covers its own instance, so correctness holds. Wraparound handling of the counter is harmless. One consequential performance side effect is listed under follow-ups.

**S64-R3-2 (file-backed mremap growth and EOF): VERIFIED.**
Each registry entry now retains a dup'd descriptor at note time (`sysmem_file_note_map`), split survivors clone it, and drops close it. Growth runs through `sysmem_file_fill_growth` in `src/os/sysmem_file_fill.c` after `sysmem_file_remap_update` extended coverage and before commit. It reuses the same populate path as the initial mmap fill, so the partial EOF page zero-fills and full pages beyond the fresh `fstat` size convert to BUS with paired TLB and DBT invalidation. Private and shared kinds are derived from the entry, chunk states are patched back onto the entry, and anonymous tails stay zero. The in-place NOMEM rollback unmaps the tail, re-excises coverage, invalidates, and aborts the transaction. Two gaps are minor and listed as follow-ups: a moved growth that hits NOMEM is not rolled back, and the retained descriptors consume host fd budget.

**S64-R3-3 (non-evicting file-range registry): REGRESSION.**
The eviction is gone. The table is growable, `sysmem_file_reserve` runs before the 6-step legs in both mmap and mremap, worst-case slot counting in `sysmem_file_span_extra` looks correct, and a failed note rolls the mapping back. However, growth is implemented with `realloc` on the table, and `sysmem_file_claim_free` now calls `sysmem_file_reserve(1)` and therefore can move the table. In `sysmem_file_drop_map`, the split path claims a tail slot and then keeps using the pre-claim `slot` pointer at `src/os/guest_run_sysmem_file.c:317` onward to read its fd, dev, ino, offset, and chunk states. Nothing reserves ahead of the munmap drop leg, so when all slots are live, a munmap that splits a file mapping reallocates and then dereferences freed memory. This is reachable through the ordinary ELF loader pattern of mapping a whole object and unmapping the gap between segments once a process has 64 live file entries. The same hazard exists for MAP_FIXED replacement over the middle of a file mapping. Before this commit `claim_free` returned NULL when full and never moved the table, so this is new.

**S64-R3-4 (Darwin guest futex dispatch): PARTIAL.**
The dispatch is wired. WAIT and WAIT_BITSET go through `thr_darwin_futex_wait` and WAKE and the ctid clear-on-exit wake go through `thr_darwin_futex_wake`, both in the new `src/os/threads_darwin.c`, which the Makefile adds to the Darwin object list. Keys are private over pid and guest VA, the backing is retained across the unlocked sleep, the value is re-verified through the copy layer after wakeups, alignment is validated on both backends, and guest-visible errnos use fixed Linux numbers. Key-based matching also handles a COW copy during the sleep. Two things fall short of the audit's ask. First, the per-thread worker signal state is a dead object: no engine code calls `rt_host_worker_sync_init` apart from this new TU, the Darwin backend keeps no thread-local or key to find it from a signal handler, and the only `sig_seq` increment is inside the backend at `src/os/backend_darwin_sync.c:188` with no producer that can reach this instance. Preemption and guest signals therefore never interrupt the Darwin wait; it relies on 10 ms cond-wait slices. Second, the `-4` branch in `thr_darwin_futex_wait` continues the loop without refreshing `expected_seq`, so if a producer is ever connected, the next `rt_host_futex_wait_bitset` call returns `-4` immediately and the wait spins at full CPU while holding and dropping the big lock until the value changes. The Linux path avoids this because the kernel consumes the signal. Latent today, but it is the exact path the fix claims to deliver.

**S64-R3-5 (Darwin worker unregistration): PARTIAL.**
Unregistration is correct and complete: `darwin_worker_unregister` exists, `rt_host_unregister_self` is exported, `vm64_worker_unregister` calls it on both exits, the spawn trampoline releases its slot after the worker returns, and `thr_darwin_ws_teardown` releases the sync state on thread exit. Double unregistration is idempotent. Table exhaustion is now reported as id 0, but the propagation stops there: `vm64_worker_register` at `src/vm/vm64.c:721` silently returns on 0, and its single caller at `src/os/guest_engines.c:380` ignores the outcome. A thread past the 256-slot limit runs without a quiescence slot, so peer mapping mutations proceed without parking it. That is the "silently running without preemption" outcome the commit message says is avoided. With the leak closed it now needs 256 concurrent threads, so the practical exposure is low.

**S64-R3-6 (directory cache eviction): VERIFIED.**
A full cache now returns `-12` after closing the freshly dup'd stream, at `src/os/backend_darwin.c:457`. No existing stream, pending entry, or descriptor offset is disturbed and no fd leaks. The cap of 32 concurrent streams is now a hard limit until a slot frees on close, which is the second alternative the audit named. Backend-only reachability is unchanged.

**S64-R3-7 (clock_nanosleep deadline): VERIFIED, with one pre-existing caveat.**
The relative path computes a monotonic deadline, rounds each bounded poll interval up to the next millisecond, caps at `INT_MAX`, and loops until the remaining time reaches zero. Only pipe readiness, `EINTR`, or a `sig_seq` step return early with `-4`, and remaining time is reported from the deadline only for relative sleeps. The fallback `nanosleep` when no worker sync exists is unchanged. The absolute path passes the Linux clock id straight to the host `clock_gettime` both in the pre-existing head at `src/os/backend_darwin_sync.c:255` and in the new loop around line 323. Linux `CLOCK_MONOTONIC` is 1, which Darwin does not define, so an absolute monotonic sleep returns `-EINVAL`. This predates the commit and has no guest caller, but the fix now repeats it.

**Curated C11 and size discipline: VERIFIED by static inspection.**
No `#include "*.c"` anywhere under `src`, `include`, or `tests`. Every touched `.c` and `.h` is at or under 900 lines; `threads.c` is at 897, `vm64.c` at 879, and `proc.c` at 842, so the next change to any of those will need a split. The new TUs compile to an empty typedef off Darwin, which keeps `-pedantic` quiet. The Darwin-only `_POSIX_C_SOURCE` definitions precede all includes. The sigaltstack alias fix and the execve disposition reset are correct and outside the R3 scope.

## Newly discovered consequential follow-ups

1. **Use-after-free in registry splits (High, new).** `sysmem_file_claim_free` can `realloc` the table while `drop_map` and `remap_update` hold a `slot` pointer into it. Fix by reserving worst-case slots before the munmap and MAP_FIXED drop legs, or by re-deriving `slot` from its index after every claim, or by growing in chunks that never move. Add a regression that fills 64 entries and unmaps the middle of one.
2. **Full DBT flush on every own-thread mapping syscall (Medium, new, performance).** `seen_epoch` only advances at the loop-top check, so a thread's own mmap, munmap, or mprotect bumps the generation and triggers a full `sparc64_dbt_invalidate` on its next iteration. Single-threaded allocator-heavy programs now discard all translations on each mapping change. Per the project rule, instrument and measure before changing it; a likely fix is to publish the generation per range or to resynchronise `seen_epoch` after the thread's own commit, since its ranged invalidation already happened.
3. **Darwin futex wait never sees signals, and would spin if it did (Medium, latent).** See S64-R3-4. Refresh `expected_seq` after each `-4`, and decide whether the engine should own and register the per-thread worker sync so preemption and guest signal delivery can reach a sleeping waiter.
4. **Retained descriptors consume host fd budget (Medium).** Every live file mapping and every split survivor holds a dup'd fd without `FD_CLOEXEC`. macOS defaults to a 256 soft fd limit, so a guest with roughly a hundred file mappings starts failing its own opens, and `dup` failures silently degrade growth to zero tails. Consider `F_DUPFD_CLOEXEC`, sharing one fd per `(dev, ino)` with a refcount, and confirm the guest fd table cannot `dup2` onto a retained host fd number.
5. **Worker-table exhaustion is swallowed (Low).** `vm64_worker_register` should fail the clone, or at least refuse to run guest code, when the backend returns id 0.
6. **Moved mremap growth ignores NOMEM (Low).** `src/os/guest_run_sysmem.c:668` only rolls back when `dest == old_addr`; a moved growth that fails the tail fill commits with a zero tail.
7. **Absolute Darwin clock_nanosleep uses an untranslated clock id (Low, pre-existing).** Map Linux clock ids to host ids before `clock_gettime` in both places.
